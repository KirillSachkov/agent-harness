# Как писать и поддерживать AGENTS.md

Агент (Claude Code), 12 ноября 2026 года. Это исследование и предложения: правила, скиллы и `AGENTS.md` ни в одном репозитории не менялись.

Источники с цитатами и датами собраны в приложении [2026-11-12-agents-md-sources.md](2026-11-12-agents-md-sources.md). Ниже ссылки вида S3 или E1 ведут на строки его таблицы источников. Приложение написано на английском, потому что цитаты в нём дословные.

## Коротко

1. **Отдельный скилл не нужен.** `writing-for-agents` уже содержит главные принципы: указатели, две нагрузки, отказ от копий того, что агент найдёт сам, удаление устаревшего. В нём нет трёх вещей: что именно класть в корневой файл, как файлы читают Claude Code и Codex, и порядок аудита существующего файла. Их стоит добавить отдельным файлом-веткой внутри `writing-for-agents`, так же как там уже лежит `SKILL-MECHANICS.md` для скиллов.
2. **Источники сходятся в одном:** в `AGENTS.md` пишут только то, что агент не узнает из кода и конфигов. Это точные команды проверки, ловушки, решения вне репозитория и то, что агенту уже дважды пришлось поправлять. Обзор архитектуры и структуру папок Anthropic теперь прямо называет устаревшим советом (S3), а самое крупное исследование не нашло от обзоров пользы (E1).
3. **В ai-first-platform корневой `AGENTS.md` устарел не только в указателе на `docs/first-version.md`.** В нём нет описания проекта в одно предложение и главной команды проверки. Codex, запущенный из корня, не видит `apps/api/AGENTS.md` и `apps/web/AGENTS.md`. Два указателя срабатывают почти на любую задачу.
4. **Для скиллов Matt предлагаю хранить нетронутую копию upstream** в `.agents/upstream/mattpocock/` и показывать отличия скриптом. Обновление тогда делает трёхстороннее слияние `git merge-file` по каждому файлу.

## Что говорят источники

Главные правила, с которыми согласны почти все первичные источники:

| Правило | Кто поддерживает | Где расходятся |
| --- | --- | --- |
| Корневой файл короткий | S1, S2 (до 200 строк), S3, S7 (32 KiB на все файлы вместе), S15 | Цифры не измерены. Ссылка на «150–200 инструкций» восходит к E4, а там проверяли написание отчёта, а не программирование |
| Только то, чего агент не найдёт сам | S3, S2 (`/doctor`), S14 (`writing-for-agents`: кэш окружения, no-op), E1 | agents.md (S5) и Copilot (S10) всё ещё советуют обзор проекта |
| Точные команды проверки, особенно для одного теста | S3 называет это самой полезной строкой, S5, S10 | S1 и Cursor (S11): только нестандартные команды |
| Без IMPORTANT, ALWAYS и капса | S1, S3: от акцента агент применяет правило там, где не нужно | Copilot (S10) советует «always» |
| Обязательное правило уходит в хук, CI или линтер | S3, S2, S7, S11, S15, `retro` Matt | Нет расхождений |
| Подробности уходят в отдельные документы по указателю | S1, S2, S3, S11, S14 | `@`-импорт Claude Code грузит файл сразу и контекст не экономит (S2). Codex `@` не раскрывает |
| Противоречий нет | S1, S2: из двух противоречащих строк Claude может выбрать любую | Нет расхождений |
| Пишет человек, генератор даёт только черновик | S1, S15, E1: файлы людей лучше сгенерированных примерно на 7% | Anthropic и Codex предлагают `/init`, но Anthropic добавляет, что дальше работа в основном в удалении строк |

Как поддерживать файл:

- **Добавлять строку**, когда агент ошибся второй раз, ревью поймало то, что агент должен был знать, или ты повторяешь ту же поправку (S2, S3, S11).
- **Регулярно удалять** устаревшее, противоречивое и то, что агент делает и без строки (S1, S2, S14). Без этого файл обрастает слоями, Matt называет это sediment.
- **Проверять ссылки и команды инструментом.** В Claude Code `/doctor prompt-audit` ищет мёртвые ссылки, несуществующие команды и противоречия, в том числе в `AGENTS.md` (S2). У нас ссылки уже проверяет `scripts/check.py`.
- **Проверять, что загрузилось:** `/context all` или `/memory` в Claude Code, вопрос «Summarize the current instructions» в Codex (S2, S7).

Пользы от файлов в целом измерено мало. E1 (ETH, 2026): файлы не дали значимого прироста решённых задач и подняли стоимость примерно на 20%. E2: с `AGENTS.md` агент работал на 29% быстрее при той же доле решённых задач, но выборка маленькая. Отсюда вывод для нас: каждая строка должна менять поведение агента, иначе она только стоит денег.

## Как файл читают наши клиенты

Это факты из документации, для Codex ещё и из исходников (S2, S7, S8). Установлены Claude Code 2.1.316 и Codex 0.167.0.

- **Claude Code с версии 2.1.277 сам читает `AGENTS.md`**, если в папке и выше нет `CLAUDE.md`, `.claude/CLAUDE.md` и `CLAUDE.local.md`. Симлинк `CLAUDE.md -> AGENTS.md` в agent-harness считается как `CLAUDE.md`, поэтому текст грузится один раз. Через симлинк Claude не может редактировать: инструмент Edit отправит его к `AGENTS.md`.
- **Claude Code подгружает вложенные `AGENTS.md` и `CLAUDE.md` лениво**, когда читает или меняет файл в этой папке.
- **Codex склеивает `AGENTS.md` от корня git до папки, где его запустили.** Вложенный файл глубже рабочей папки он не читает. Если Codex запущен из корня, `apps/api/AGENTS.md` он не увидит.
- **У Codex лимит 32 KiB на все файлы вместе**, остаток обрезается с предупреждением. `CLAUDE.md` и строки `@path` Codex не читает, поэтому указатели пишем обычными Markdown-ссылками.
- **`CLAUDE.local.md` отключает чтение `AGENTS.md`** в Claude Code, если нет симлинка или импорта. Симлинк работает при любой настройке и в старых версиях.

## Хватает ли writing-for-agents

`writing-for-agents` даёт принципы, которые решают большую часть вопроса:

- строка в `AGENTS.md` с упоминанием документа считается указателем, и от её формулировки зависит, когда агент откроет документ;
- каждая строка постоянно загруженного файла тратит контекст на каждом ходу;
- одно значение хранится в одном месте;
- то, что агент найдёт в `package.json` или структуре папок, в файл не копируется;
- строки, которые не меняют поведение агента, удаляются целиком.

Это ровно те правила, которых требует владелец: файл полезен любой сессии, в нём только нужное и без дублирования.

Чего в нём нет:

1. **Состава корневого файла.** Описание проекта в одно предложение, команда проверки перед PR, ловушки, указатели на вложенные файлы и тематические документы. Сейчас агент выводит это из общих принципов, и каждый раз по-разному.
2. **Механики клиентов.** Как Claude Code и Codex находят файлы, что Codex не видит вложенный файл ниже рабочей папки, лимит 32 KiB, симлинк или импорт, `@` против обычной ссылки.
3. **Порядка аудита существующего файла.** Пройти каждую строку и решить: оставить, перенести в документ по указателю, перенести в проверку или удалить. Проверить, что каждый путь, команда и ссылка существуют. Найти то же правило в `docs/agents/` и скиллах. Показать владельцу разницу до правки.
4. **Создания с нуля.** `setup-matt-pocock-skills` уже пишет в `AGENTS.md` язык и указатели на `docs/agents/`, но не описание проекта, команды и ловушки.

### Варианты

- **А. Дополнить `writing-for-agents` (рекомендую).** Новый файл `AGENTS-MD.md` рядом с `SKILL-MECHANICS.md` с пунктами 1–4 выше. В `SKILL.md` добавится одна строка-указатель, как уже сделано для скиллов, а в описание скилла слово про аудит. Новое постоянно загруженное описание не появляется, принципы не дублируются. Это меняет текст Matt в двух строках, поэтому зависит от решения по копии upstream ниже.
- **Б. Отдельный скилл `agents-md`, который вызывает только человек.** Процедура «создать или проверить `AGENTS.md`», принципы он берёт из `writing-for-agents`. Контекст не тратит, но ты должен помнить, что он есть. Подходит, если хочется явной команды вида «/agents-md». Скилл, который агент вызывает сам, не советую: его описание совпало бы с описанием `writing-for-agents`, и агент выбирал бы между ними наугад.
- **В. Ничего не добавлять.** Аудит делать `/doctor prompt-audit` и скиллом `retro`. Это дешевле всего, но Codex такого аудита не имеет, и состав корневого файла каждый раз будет другим.

Плагин Anthropic `claude-md-management` как основу не советую. Его последний коммит от 20 февраля 2026 года, `AGENTS.md` он не знает, ищет файл `.claude.local.md` вместо `CLAUDE.local.md` и высоко оценивает раздел об архитектуре, который Anthropic теперь советует удалить (S4).

## Разбор ai-first-platform

Проверял `main` на `832f9da`. Корневой `AGENTS.md` занимает 25 строк и 2 642 байта, оба вложенных файла вместе с ним дают около 7,7 KB, до лимита Codex далеко. `CLAUDE.md` в репозитории нет, поэтому Claude Code 2.1.316 читает `AGENTS.md` сам.

### Устарело

1. **Указатель на `docs/first-version.md`.** Документ записывает решение задачи #2 от 29 октября. После этого границы уточнили карта #1 и спецификации #48–#50. Строка 17 («один или несколько репозиториев») противоречит решению владельца из #52, что проект может быть без репозиториев (аудит, О4). Требование «прочитать перед любой работой» заставляет каждую сессию сверять бриф, этот документ и задачи между собой. На тот же документ ссылаются `docs/agents/domain.md` и `README.md`.
2. **Указатель на `customer-requirements.md` перед любой работой.** Это исходный бриф. Строка рядом сама говорит, что согласованные изменения важнее брифа, то есть агент читает документ, который потом должен частично отбросить.

Варианты для обоих: указывать на карту #1 и спецификацию задачи как на источник границ, а `first-version.md` пометить как запись решения #2 или вынести в историю задачи #2. Что делать с документом, решаешь ты.

### Не хватает

1. **Описания проекта в одно предложение и стека.** Сейчас корневой файл не говорит, что это за продукт. S1 и S3 считают это первой строкой файла. В `README.md` это есть, но README агент открывает не всегда.
2. **Главной команды проверки.** `pnpm verify` перед PR и запуск одного теста описаны только в `docs/agents/testing.md` за указателем. S3 называет эту строку самой полезной в файле.
3. **Указателей на `apps/api/AGENTS.md` и `apps/web/AGENTS.md`.** Codex, запущенный из корня репозитория, эти файлы не читает. Правила о `@Inject`, часах и `pnpm db:generate` до него не доходят. Нужна строка вида «Before changing `apps/api`, read `apps/api/AGENTS.md`».
4. **Правил передачи между сессиями из аудита.** Занять задачу до записи, менять объём в задаче, писать «по решению владельца» только с цитатой, одобрение через посредника (аудит, раздел «Правила передачи между сессиями»). Им место в `docs/agents/issue-tracker.md`, `delivery.md` и `human-review.md`, а в корневом файле достаточно существующих указателей.
5. **Правила старта для обычной речи (аудит, П4).** Оно живёт в корневом `AGENTS.md`, и аудит оставил вопрос тебе: считать ли «запусти задачу N» выбором `implement`.

### Дублируется или лишнее

1. **Фраза «project rules win» записана дважды:** в корневом `AGENTS.md` и в `docs/agents/delivery.md`. Кроме того, она есть строкой в адаптациях `implement` и `implement-spec`.
2. **Служебные фразы, которые не меняют поведение:** «This section owns the language setting» и «`README.md` is for people» внутри указателя на delivery.
3. **Слишком широкие условия указателей.** Domain guidance читается «before domain design, exploration, implementation, or review», delivery «before implementation, a review round, or delivery». Это почти любая задача, поэтому указатель срабатывает всегда. Тогда нужное из этих документов стоит либо перенести в корень, либо сузить условие.
4. **История в правилах.** `testing.md` начинается со строки «Agreed with the owner in #14 and specified in #19». Агенту она ничего не говорит.

### Что в порядке

Вложенные `apps/api/AGENTS.md` и `apps/web/AGENTS.md` написаны так, как советуют источники: ловушки, которые не видны из кода, команды генерации и ссылки на образцы вместо пересказа.

## Копия upstream для скиллов Matt

Сейчас в agent-harness записан только SHA upstream `a496f55`, а хэши в `.agents/skills/README.md` считаются по нашим изменённым копиям. Чтобы увидеть отличия, нужно скачать upstream отдельно. В ai-first-platform так же: `diff -r <upstream>/... .agents/skills/<skill>`. Matt после `a496f55` сделал 4 коммита, и ни один не трогает `writing-for-agents` (S14).

### Рекомендую: нетронутая копия в репозитории

```text
.agents/
  skills/                     рабочие копии, их читают клиенты
  upstream/mattpocock/
    SOURCE                    SHA upstream и дата
    skills/<group>/<skill>/   файлы upstream без изменений, только наши 27 скиллов
scripts/
  upstream.py                 diff и update
```

1. **Где копия.** `.agents/upstream/mattpocock/` повторяет раскладку upstream. Claude Code ищет скиллы в `.claude/skills`, Codex в `.agents/skills`, поэтому копию они как скиллы не подхватят.
2. **Как видно отличия.** `python3 scripts/upstream.py diff` печатает разницу между копией upstream и `.agents/skills` по каждому скиллу. Список адаптаций в README остаётся одной строкой на скилл с причиной, а сами строки показывает diff.
3. **Как переносить обновление.** `upstream.py update <sha>` кладёт новую версию upstream во временную папку и для каждого файла запускает `git merge-file <наш файл> <старый upstream> <новый upstream>`. Конфликты остаются в файле для ручного разбора. Потом копия upstream заменяется новой, и всё уходит одним PR с ревью, как требует [upstream.ru.md](../upstream.ru.md).
4. **Как защитить копию от правок.** `scripts/check.py` сверяет хэш папки upstream с записанным в `SOURCE`. Случайная правка копии роняет CI.

Это не противоречит границам первой версии: нет установщика, автосинхронизации и submodule, обновление запускает человек.

Альтернатива: отдельная ветка `upstream/mattpocock` с чистым upstream и `git subtree` для слияния. Git сам сделает трёхстороннее слияние, но раскладка upstream (`skills/<group>/<skill>`) не совпадает с нашей (`.agents/skills/<skill>`), а копия не видна в обычном дереве файлов. Поэтому её не советую.

## Что не проверено

- Измерений по отдельным практикам нет: ни одно исследование не сравнивало длину файла, вложенные файлы или указатели против текста в корне (E1–E4).
- Codex я не запускал. Поведение со вложенными файлами взято из документации и исходного кода (S7, S8).
- Предложенный состав корневого файла ai-first-platform на живых сессиях не проверялся.
