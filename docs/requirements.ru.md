# Согласованные границы

[English](requirements.en.md)

Это личный публичный пример harness Кирилла Сачкова.
Первая версия сохраняет рабочий путь от issue до PR и позволяет проводить дальнейшие эксперименты.
Это пример процесса; приложение и универсальная система конфигурации в поставку не входят.

## Требуемое поведение

- Каждая реализация имеет ограниченную issue; полная spec нужна по сложности.
- Владелец явно выбирает реализацию. Согласованный spec run может делегировать свои tickets.
- Независимые реализации используют отдельные worktrees; продолжение использует назначенную копию.
- Standards и Spec reviewers получают свежий контекст. Исправления проходят затронутые проверки и независимое ревью.
- `ship` доставляет проверенный PR; каждый итоговый PR принимает владелец.
- Агентские инструкции остаются английскими. Человеческая работа использует выбранный EN/RU-режим с равными возможностями.
- Setup через беседу выбирает язык и сохраняет существующие настройки проекта.
- Редактируемые копии upstream сохраняют версии, уведомления и адаптации. Обновления проверяются вручную.

## Ограничения

Человеческие карты объясняют правила. AGENTS и тематические агентские документы определяют полномочия.
Настройки защиты GitHub существуют отдельно от письменных правил.
Установщик, auto-sync, classifier ревью, автоматический merge и eval framework в первую версию не входят.
Численный предел ревью и отдельный арбитраж замечаний остаются гипотезами.
Будущие изменения получают issues, проверки и ревью, соответствующие фактическому поведению.
