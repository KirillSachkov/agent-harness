# Proposed experiments

[Русский](experiments.ru.md)

Status: proposed; no comparative experiment has been executed.
The workflow’s effectiveness remains a hypothesis despite structural checks and static reviews.

## First observations

Use the current baseline on two or three ordinary tasks before adding more rules.
Keep issue criteria, initial/final commits, skill revision, client/model, review reports, corrections and actual check results.
Record unnecessary changes, repeated findings, owner questions and available time/cost data.
Keep private correspondence, credentials and raw session logs outside the public repository.
Publish only suitable original summaries and source references.

## Compare later

| Question | Comparison | Useful observations |
| --- | --- | --- |
| Does correction review help? | Checks after fixes versus checks plus independent correction review | Remaining defects, regressions, rounds, time and cost |
| Do detailed loops help? | Short sequential steps versus an explicitly bounded loop | Missed actions, extra changes and owner intervention |
| Is a round cap useful? | Current progress-based stopping versus a numerical cap | Stalls, unresolved defects and unnecessary escalation |
| How should false findings close? | Existing visible dispute handling versus independent rejection verification | False positives, missed defects and owner effort |
| Is resumption clear? | Current instructions versus an explicit assignment-lifetime rule | Correct scope and unintended starts |

Use equivalent source snapshots, expectations and model settings for a comparison.
Set a limited run budget before starting; this is an experiment condition rather than a new production rule.
Have an independent evaluator judge the result, hiding the variant name when practical.
Choose an outcome that would reject the proposed change before running it.
Retain a change when observations show useful benefit at acceptable cost; revise it when they do not.
Small samples provide observations, not universal proof.

## Deferred changes

There is no new numerical review cap, arbitration role, classifier or automatic synchronization.
Do not turn every hypothetical failure into another instruction.
A concrete issue can later introduce a case, variant or eval when its expected result is clear.
