# Определения

Термины DDD и EventStorming, которыми мы пользуемся, и зачем каждый нужен. Определения следуют источникам из [sources.md](sources.md).

## Стратегический DDD: язык и границы

| Термин | Что это | Зачем нужен |
|---|---|---|
| Домен (domain) | Область деятельности, для которой пишется программа | Задаёт предмет разговора |
| Поддомен (subdomain) | Часть домена, отдельная бизнес-задача. Существует и без программы | Решить, куда вкладывать силы |
| Основной поддомен (core) | То, чем продукт отличается от других | Здесь нужна лучшая модель и самое внимательное проектирование |
| Вспомогательный поддомен (supporting) | Нужен основному, но преимущества не даёт | Делаем просто |
| Типовой поддомен (generic) | Задача, которую уже решили до нас: вход, оплата, почта | Берём готовое решение |
| Единый язык (ubiquitous language) | Слова, которые одинаково понимают люди и код | Убирает перевод между бизнесом и кодом |
| Bounded context, ограниченный контекст | Граница, внутри которой у каждого слова один смысл и действует одна модель | Модель остаётся цельной, а разные части системы могут понимать одно слово по-разному |
| Карта контекстов (context map) | Схема контекстов и отношений между ними | Видно, кто от кого зависит и кто под кого подстраивается |
| Модуль | Способ разложить код | Удобство разработки. Границу смысла модуль сам не задаёт |

Поддомен делит задачу, контекст делит решение. Удобно, когда один контекст закрывает один поддомен, но так бывает не всегда. Контекст может состоять из нескольких модулей. В модульном монолите модуль часто совпадает с контекстом, и это стоит проверять: если одно слово значит разное в двух модулях, это два контекста.

### Отношения на карте контекстов

Вышестоящий контекст (upstream) влияет на нижестоящий (downstream).

| Отношение | Что значит |
|---|---|
| Customer/Supplier | Нижестоящий заказывает, вышестоящий учитывает его нужды |
| Conformist | Нижестоящий принимает чужую модель как есть |
| Anti-corruption layer | Нижестоящий ставит слой перевода, чтобы чужая модель не проникала внутрь |
| Open host service | Вышестоящий даёт открытый протокол для всех желающих |
| Published language | Общий описанный формат обмена: события, схема |
| Shared kernel | Два контекста делят небольшую общую часть модели |
| Partnership | Два контекста развиваются согласованно |
| Separate ways | Контексты не связаны |

## Тактический DDD: сложные правила в коде

Нужен только там, где логика сложная.

| Термин | Что это | Зачем нужен |
|---|---|---|
| Сущность (entity) | Объект, который остаётся собой при изменениях: у него есть идентичность | Следить за объектом во времени |
| Объект-значение (value object) | Значение без идентичности, сравнивается по содержимому | Делает правила о значениях явными |
| Агрегат (aggregate) | Группа объектов, которая меняется как одно целое и сама охраняет свои правила | Граница согласованности: правило внутри агрегата верно всегда |
| Инвариант | Правило, которое должно быть верно после каждого изменения | Определяет границы агрегата |
| Доменное событие | Факт, который произошёл в домене, в прошедшем времени | Связывает шаги процесса |
| Интеграционное событие | Событие, опубликованное для других контекстов | Передаёт изменения через границу |
| Репозиторий | Способ достать и сохранить агрегат, не раскрывая хранилище | Отделяет правила от базы данных |
| Доменный сервис | Правило, которое не принадлежит одному объекту | Место для такой логики |

Между агрегатами ссылаются по идентификатору. Правило, которое связывает несколько агрегатов, обеспечивается отдельно: событием, блокировкой или ограничением базы.

## EventStorming

| Термин | Что это |
|---|---|
| Событие | Что произошло. Основа всей схемы |
| Действие (command) | Что участник или система решили сделать |
| Участник (actor) | Роль, которая выполняет действие |
| Реакция (policy) | Правило «когда произошло X, сделать Y». Действие выполняет система |
| Данные, на уровне кода агрегат | То, что действие меняет |
| Что видит участник (read model) | Сведения, по которым участник принимает решение |
| Внешняя система | Система за пределами нашей |
| Открытый вопрос (hot spot) | Место, где неясно или есть спор |
| Ключевое событие (pivotal event) | Событие, после которого процесс переходит к другой части области. Кандидат в границу |

У EventStorming три уровня. Big Picture охватывает всю область. Process Modelling разбирает один процесс. Software Design доходит до агрегатов и кода.

## Соседние практики

| Термин | Что это |
|---|---|
| Example Mapping | Разбор правила на примерах: правило, под ним конкретные случаи, рядом вопросы |
| ADR | Короткая запись архитектурного решения: что решили, из чего выбирали, какие последствия |
| Спецификация | Требования к изменению: истории и критерии приёмки |
